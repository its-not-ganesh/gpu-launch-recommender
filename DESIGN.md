# Architecture-aware CUDA launch recommender

Phase 1 specification for NYU Courant GPU Project 6. The implementation target is `cuda2` with CUDA 13.0 and `sm_75`. See [STATUS.md](STATUS.md) for observed hardware and [PLAN.md](PLAN.md) for submission gates. Model preferences below are hypotheses.

## Architecture and launch candidates

- **DeviceInfo** selects one CUDA device and records its name, compute capability, SM/warp counts, thread/block/grid limits, SM and block limits for registers and shared memory, and runtime/driver versions. Read properties with `cudaGetDeviceProperties`, including the maximum resident blocks per SM. The observed RTX 2080 Ti has 68 SMs, 32 lanes per warp, and 32 maximum resident warps per SM.
- **KernelSpec** holds the kernel ID, entry points, 1D or 2D geometry, grid-stride traversal, work class, per-element work and logical bytes, block-shape restrictions, dynamic shared memory function, and the reduction's fixed final stage. Query per-entry-point limits, registers per thread, and static shared memory with `cudaFuncGetAttributes`. **Workload** holds N or W/H, deterministic seed, and element type (FP32). Use checked 64-bit arithmetic for products, strides, and ceiling division before narrowing dimensions to `dim3`.
- **Launch** holds grid and block tuples and per-stage dynamic shared memory. For 1D, enumerate block sizes 64, 128, 256, and 512. Let T = ceil(N / block.x). For 2D use (8,8), (16,8), (32,4), (16,16), and (32,8). Let Tx = ceil(W / block.x), Ty = ceil(H / block.y), and T = Tx × Ty. Unused dimensions are 1. Grid-stride steps are blockDim × gridDim on the relevant axes. Each logical tile is visited exactly once, including guarded partial tiles.
- For each block shape, consider CTA budgets of 1, 2, and 4 per SM plus full coverage. For 1D use grid.x = min(T, budget, grid limit). In 2D, first clip Tx and Ty to device limits. For budget G, set gx = min(Tx, G), gy = min(Ty, floor(G/gx)) using the clipped dimensions. Use the clipped (Tx,Ty) for full coverage. The cap distributes work across rows once a full tile row fits. Deduplicate by complete launch tuple. For reduction bound every stage-1 grid by 4 × SM count, including the coverage candidate. Always include both feasible fixed baseline launches in the measured set.
- **Feasibility** checks positive dimensions, axis limits, block volume against device and function caps, kernel shape restrictions, checked arithmetic, and static plus dynamic shared memory against the default block limit. Use `cudaOccupancyMaxActiveBlocksPerMultiprocessor` with each stage's actual block size and dynamic shared memory to account for register and shared-memory allocation granularity and SM limits. Reject zero residency. Preflight checked allocation sizes and surface allocation errors. Keep the GPU selection, allocations and arithmetic identical across roles. [CUDA occupancy API](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-runtime-api/group__CUDART__OCCUPANCY.html)

## Analytical selection and baselines

For each feasible launch let G be its physical stage-1 CTA count, t its threads/block, R the CUDA-reported resident CTAs/SM, and S = SM count × R. Let A = min(G,S) × ceil(t/warp) / (SM count × max warps/SM). Let U = G / (min(G,S) × ceil(G/S)) estimate CTA utilization of scheduled waves. Let E = elements/(T × t) capture partial tiles, using unclipped logical tile counts. Let C = min(1, block.x/warp) for the row-major transform and 1 otherwise. Let q = min(1,G/T). Minimize

```text
cost = (1 + l*(1-q) + d*q + p) /
       (min(1,A/a) * (0.75+0.25*U) * E * C)
```

Use (a,l,d) = (0.50,0.10,0.18) for vector add and transform, (0.75,0.15,0.05) for compute, and (0.50,0.10,0.05) for reduction. Use p = 0 except for reduction, where p = 0.20 × G/(4 × SM count) represents partial-result traffic and final-stage work. Cost is dimensionless. The occupancy term saturates, while useful lanes, wave tails, grid-stride loop pressure and scheduling overhead still influence ranking. The 2D coalescing factor is a shape preference, and U approximates CTA waves without modeling unequal CTA durations. Tie-break by smaller G, then lexicographic block and grid dimensions. Explain the chosen dimensions, occupancy, limiting resource inputs, and significant penalties. Normal use queries metadata and ranks candidates on the host with zero kernel launches or timings.

Fixed baselines are 128 and 256 threads for 1D, and 16×8 and 16×16 for 2D, each with coverage or the reduction cap. The **CUDA occupancy-based baseline** maximizes `R × ceil(t/warp)` among legal block shapes with its corresponding coverage grid or reduction cap. Break ties by fewer threads, then lexicographic shape. It uses the same compiled kernel and the CUDA residency API, with no grid search, saturation, tile-efficiency or workload terms. Mark any unavailable fixed baseline explicitly. The empirical reference is the minimum median among all tested valid unique launches, including both baseline types and the recommendation. Timed duplicates share one launch ID and sample set.

The implementation records model revision `analytical-v1`. CSV roles are `candidate`, `fixed_1`, `fixed_2`, `occupancy`, `recommended`, and `empirical_best`. The metadata records each selection's launch ID or `unavailable` for a missing baseline. The empirical role is assigned using median normalized event times after a successful evaluation. Exact median ties use the smallest launch ID. Recommendation output reports both the per-SM resident occupancy and `estimated_occupancy`, the grid-limited quantity A used by the score.

## Required benchmark suite

All inputs use deterministic seed 3175 by default and bounded, finite values. Use the candidate shapes and grid policies above. C denotes calibration, H denotes held-out. Small and irregular correctness-only cases are listed separately below.

| Kernel | Work and correctness | Workloads | Architectural hypothesis |
|---|---|---|---|
| `vadd` | Grid-stride FP32 `z[i]=x[i]+y[i]`. Use signed dyadic input and compare every output exactly against the CPU. Logical traffic 12 B/element. | C: 262144. H: 1048583 and 16777216. | Large cases may favor coalescing and memory throughput once latency is sufficiently hidden. Small cases may be sensitive to CTA count and cache. |
| `compute` | Grid-stride 128 dependent FP32 `fmaf(r,a[i],b[i])` steps per element, beginning at `x[i]`. Generate deterministic inputs that keep values bounded, with nonconstant initialization and coefficients. Use CPU `std::fma` with the same recurrence. Compare all finite outputs with abs error ≤ 1e-6 + 1e-5 × abs(reference). Logical work 256 FLOPs and 16 B/element. | C: 131072. H: 32771 and 1048583. | Dependent FP32 arithmetic may benefit from additional resident warps and enough CTAs to fill SMs. |
| `reduce` | Each thread accumulates FP32 grid-stride input, then each power-of-two CTA performs a shared-memory tree with synchronized levels and emits one partial. Stage 2 uses one 256-thread CTA, grid-stride reads of all partials, and the same tree to emit one result. Use seeded 0/1 input with the last element forced to 1 and N ≤ 2^24, so all partial sums are exact FP32 integers. Compare to exact CPU integer sum and separately test all-ones and tail impulses. Dynamic shared bytes are 4 × stage block size. | C: 262144. H: 1048583 and 16777216. | Block size, synchronization, per-thread work, and partial count may trade off. The fixed final launch may dominate small cases. |
| `transform` | Row-major FP32 `out[y,x]=0.5*in[y,x]+0.25*in[y,W-1-x]` using independent x/y strides. Compare every output exactly with a CPU reference using bounded dyadic input. Logical reads/writes total 12 B/element including possible reuse. | C: 512×512. H: 1009×769 and 4096×3072. | Wider warp-aligned x dimensions may reduce segmented row accesses. Odd widths may increase tail waste. |

Optional after core results and packaging are secure: register-intensive kernel and 2D stencil.

## Experimental protocol

1. Allocate and initialize once per workload, prepare a CPU reference, and validate every unique launch by copying back and checking the result before timing. Use an output sentinel and ensure every expected output was written. On any launch, synchronization or validation error, return nonzero with the workload and configuration. Preserve an explicit outcome without a successful timing for the invalid configuration.
2. Use one CUDA stream and CUDA events bracketing K identical launches of the complete operation. For reduction bracket both stages in sequence for each iteration. Exclude allocations, transfers, CPU checks, logging, and event creation. Warm up with 5 complete untimed operations per candidate. Run 11 rounds of one timed batch per candidate in shuffled order (fixed seed), K = 20 by default. Synchronize the stop event and divide elapsed ms by K. Record each normalized batch, and retain exact iteration count and order. Require finite positive elapsed time and use the same K across the workload. Round means are individual observations, not 20 independent samples.
3. Same input, precision, algorithm, compiler flags, requested outputs and stream behavior for every role. Only launch shape/geometry and induced reduction partial count may change. The second kernel and its arithmetic are always included. Record the device index/UUID, pre/post load, and obvious contention. Flag compromised runs and retain raw files. Use the same uncontended GPU for comparisons. Keep primary samples even when a secondary repeat is warranted.
4. Freeze candidate policy and initial weights before calibration. Run the listed calibration cases first for correctness, practical sample duration, and sanity checks. If any heuristic weight changes, document the justification and Git revision before running held-out cases. Never use held-out timings to tune a model evaluated on those same cases. Report per-workload config counts and failed checks. Median and IQR use normalized batches with linear interpolation at p25/p75. Relative slowdown percent = 100 × (recommended median / best tested median − 1). Speedup vs a baseline = baseline median / recommended median. Report ties, losses and observed variability.
5. Raw CSV `results/raw/<run_id>.csv` records `schema_version,run_id,split,kernel,n,width,height,seed,launch_id,roles,block_x,block_y,block_z,grid_x,grid_y,grid_z,shared_bytes,final_block_x,final_grid_x,final_shared_bytes,validation_status,error_code,round,order,warmups,batch_iters,elapsed_ms,ms_per_operation`. Use blank irrelevant fields and pipe-delimited roles. Pair it with `<run_id>.meta.txt` recording UTC time, hostname, device UUID/index/name/CC/SM count, driver/runtime/nvcc and g++ versions, compiler flags, Git revision and dirty state, invocation, model revision, seeds, and GPU load snapshots. Store derived tables/plots in `results/summary/`. Treat CSV header order and schema version as fixed.

## Build and interface

- `Makefile` builds `build/gpu-launch` and supports `make`, `make check`, and `make clean`. On CIMS run `module load cuda-13.0` then `make CUDA_ARCH=75`. Use `nvcc -O3 -std=c++17 -gencode arch=compute_75,code=sm_75 -lineinfo` for the measured build. Apply identical flags to all configurations, retain standards-compliant FP behavior, and make `CUDA_ARCH` overridable. Require GNU Make, GCC/G++, the CUDA module, and an NVIDIA driver/GPU. Optional Python 3 standard library can summarize CSVs, with plotting libraries optional for local analysis only.
- `include/gpu_launch/` contains typed device, kernel, launch and measurement interfaces. `src/main.cu` handles CLI and dispatch. `src/device.cu` collects hardware and function data. `src/candidates.cpp` handles shape/geometry generation. `src/recommender.cpp` holds scoring and baseline selection from residency metadata. `src/kernels/{vadd,compute,reduce,transform}.cu` contain kernels and launch wrappers. `src/evaluate.cu` handles validation/timing/CSV, with tests under `tests/`. Preserve `phase0/` and its evidence independently.
- CLI `gpu-launch <check|recommend|evaluate> --kernel <vadd|compute|reduce|transform> [--n N | --width W --height H] [--device I]`. The workload range is 1 to 2^24 elements, including checked W×H for 2D. Require the dimension flags appropriate to the kernel. `check` accepts optional `--block X[,Y] --grid X[,Y]` together for one legal launch and otherwise checks all feasible candidates for the input. `evaluate` adds `--csv PATH --split <calibration|heldout> [--seed N --warmups N --rounds N --batch N]`. Require fresh output paths for CSV and its metadata. `recommend` emits a stable key=value record of device, kernel, grid/block tuples, shared bytes, optional final reduction launch, and score plus explanatory factors. `check` emits validation counts. `evaluate` emits run ID and CSV paths on stdout. Usage errors exit 2. CUDA, validation, and I/O failures exit 1 with contextual stderr. Successful invocations exit 0.
